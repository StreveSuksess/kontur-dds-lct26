# Контур ДДС — сопроводительная документация v3

**28 сентября 2026 · учебный прототип · синтетические данные**

Этот документ описывает текущий демонстрационный продукт, способ локального запуска и границы проверок. Он подготовлен командой проекта и не является официальным шаблоном организатора. Упражнения не подключены к действующей Системе-112, реальным службам или рабочему АРМ.

## 1. Что можно показать

| Учебный путь | Реализованное действие | Граница |
| --- | --- | --- |
| ДДС: готовая карточка | Преподаватель утверждает сценарий и назначает попытку; учащийся открывает карточку, сохраняет статусы с текстом, делает учебный исходящий доклад, сдаёт работу; преподаватель разбирает отчёт и решения по критериям. | Прототип не подтверждает соответствие рабочему регламенту или реальной маршрутизации. |
| 112: первичный приём | Отдельное текстовое упражнение на двух фиксированных синтетических вводных: заполнение полей карточки и выбор служб, сравнение с авторским эталоном, заключение преподавателя. | Нет входящего голосового диалога, территориальной маршрутизации и передачи созданной карточки в цикл ДДС. |

ДДС остаётся основной сквозной демонстрацией. Путь 112 сознательно мал: это проверяемый фрагмент второго сценария письменного задания, а не полнофункциональный приём вызовов.

## 2. Учебный цикл ДДС и время

Преподаватель готовит карточку, контакты и рубрику, утверждает версию и назначает её ученику. Назначение сохраняет неизменяемый снимок. Можно одной операцией доставить от одной до 100 заранее назначенных карточек: все получают общий серверный `started_at`. Ученик видит активную очередь и часы других карточек; переключение между ними не перезапускает отсчёт.

В текущей рубрике используются два отдельных настраиваемых учебных предела. **30 секунд** — от поступления карточки до первого `card_opened`. **3 минуты** — от поступления до первого сохранённого `status_changed` с непустым комментарием. Историческое API-поле `completion_limit_seconds` теперь обозначает именно второй предел. Сдача и завершение происшествия могут происходить позже; полная длительность показывается отдельно. При восстановлении связи серверный момент доставки нельзя считать точным моментом офлайн-действия, поэтому спорный тайминг уходит преподавателю.

Учебные статусы: «Принята», «Не принята», «Реагирование», «Прибытие», «Проведение работ», «Отказ», «Завершено» (`accepted`, `rejected`, `responding`, `arrived`, `working`, `refused`, `completed`). Статус без текста сервер отклоняет. Ожидаемая последовательность задаётся сценарием; она не объявляется универсальным оперативным регламентом. Проверка исходной карточки ДДС до принятия не добавлена в обязанности учащегося.

Отчёт связывает выводы правил с сохранёнными событиями. Преподаватель может исправить отдельный критерий с причиной и ссылкой на события, затем отдельно подтвердить общий итог. Исходный автоматический отчёт сохраняется; новая правка критерия делает прежнее подтверждение итога устаревшим. Для рекомендаций используются только пригодные подтверждённые попытки, остановленные исключены.

## 3. Отдельное упражнение 112

Ученик получает одну из двух текстовых вводных и заполняет тип происшествия, адрес, описание, имя и телефон заявителя, список служб. Программа нормализует поля для детерминированного сравнения и показывает расхождения после сдачи. Преподаватель группы добавляет обязательное заключение. Эталон скрыт до сдачи. Смысл произвольного текста и корректность реальной маршрутизации здесь не оцениваются.

Это отдельные API и таблица данных, а не начало попытки ДДС. Путь доступен для демонстрации обработки учебной карточки, но его результат не следует выдавать за проверку оператора реального входящего вызова.

## 4. Доказательства и знаменатели

Синтетический benchmark содержит **40 случаев и 48 ожидаемых утверждений**, единица анализа — утверждение. Адаптер вернул поддерживаемый статус для **28/48 (58,3%)**; среди этих 28 совпало с авторской меткой **27/28 (96,4%)**. Остальные **20/48** помечены `unsupported`, точность для них не измерена. В покрытых результатах есть четыре `manual_review`, то есть воздержание от автоматического `pass`/`fail`. Отдельная условная метрика решительных ответов — 24/24, она не меняет общий знаменатель.

Набор и разметка созданы разработчиками, без независимого методиста и без реальных операторов. Прогон 112 в этом benchmark дал 0/12, поскольку адаптер тестировал оценщик ДДС; это **не** измерение нового отдельного текстового упражнения 112. Полный разбор, включая одно расхождение, находится в `docs/evaluation-report.md`; входные данные и результат — `docs/validation-cases.json` и `docs/benchmark-results.json`.

Технические тесты подтверждают поведение конкретного кода и локальных пакетов. Они не измеряют педагогический эффект, согласованность экспертов, точность на реальных журналах, длительное занятие на целевом i5/Linux или живую очередь класса. Для этих выводов нужны независимая разметка и пилот по `docs/pilot-protocol.md`.

## 5. Локальный запуск и устройство

Для обычного запуска из корня проекта установите зависимости согласно `README.md`, затем выполните `./scripts/start.sh`. После первоначальной установки скрипт поддерживает `./scripts/start.sh --offline`. Интерфейс открывается на `http://127.0.0.1:8000`. Демоданные создаются только при `DEMO_MODE=true`; логины `teacher`, `student`, `admin` с паролем `Demo112!` предназначены исключительно для синтетической демонстрации.

Проверенный исторический офлайн-комплект RC2 относится к **macOS arm64 и CPython 3.12**. Для первой установки без сети нужен заранее установленный CPython 3.12 с `venv` и `ensurepip`, а также подготовленный wheelhouse. Команда и ограничения описаны в `docs/offline-install.md`; Linux и Windows этим комплектом не подтверждены. Модели AI и Python runtime в него не входят. Текстовый цикл работает по правилам без локальной модели.

Браузер React отправляет запросы к same-origin FastAPI. SQLAlchemy хранит попытки и события в SQLite WAL; сервер выдаёт собранный интерфейс. События клиента имеют UUID для безопасного повтора после разрыва, локальные черновик и очередь переживают временную недоступность сервера при сохранном профиле браузера. Детерминированный оценщик строит отчёт; AI-подсказки не выставляют итоговый балл. Один Uvicorn worker — проверенный режим, PostgreSQL предусмотрен конфигурацией, но не испытан.

## 7. Короткий маршрут демонстрации

| Шаг | Действие | Что проверить на экране |
| --- | --- | --- |
| 1. Преподаватель | Войти в деморежиме, открыть сценарий ДДС, проверить карточку и рубрику, назначить две попытки одному ученику. | Утверждённая версия и два назначения видны в списке. |
| 2. Поступление | Выбрать оба назначения и доставить одной операцией. | У карточек общий старт; открытие одной не останавливает часы другой. |
| 3. Учащийся | Открыть карточку, сохранить статус с содержательным комментарием, выполнить учебный исходящий доклад и завершить попытку. | Отчёт различает время открытия, первый статус с текстом и полную длительность. |
| 4. Преподаватель | Открыть отчёт, найти событие-доказательство, изменить один спорный критерий с причиной и подтвердить итог. | Исходная оценка, решение по критерию и подтверждённый итог показаны отдельно. |
| 5. Упражнение 112 | Войти учеником, заполнить одну синтетическую карточку и выбрать службы; затем открыть её преподавателем. | Сравнение появляется после сдачи; преподаватель добавляет заключение. |

Перед показом используйте отдельную демонстрационную БД и проверьте сеть и браузер на целевой машине. Если нужен повтор benchmark, команды находятся в `docs/evaluation-report.md`. Если нужен новый офлайн-архив для другой платформы, подготовьте его на машине той же архитектуры и проверьте свежую установку и smoke, как описано в `docs/offline-install.md`.
