# Объяснимые рекомендации следующего упражнения

`GET /api/recommendations` предлагает преподавателю сложность следующего упражнения по проверенной истории. Это авторская эвристика MVP, не диагностическая шкала, не прогноз готовности к реальным ЧС и не методика, утверждённая заказчиком. Назначения, баллы и пользовательские данные запрос не изменяет.

## Чьи данные учитываются

Ученик получает один элемент только о себе, включая свои попытки разных преподавателей. Преподаватель получает элементы только по ученикам, которым он сам назначал задания, и учитывает только собственные назначения. Это область видимости назначений; отдельного реестра закрепления учеников за преподавателями в MVP нет. Администратор к этому учебному API не допускается.

История фильтруется по текущему профилю службы ученика. Совместимость совпадает с назначениями: одинаковая служба; универсальный сценарий (`Учебная ДДС`, `Все службы`, `универсальная`); либо универсальный профиль ученика `Учебная ДДС`. Поле `classroom` объясняет совместимость. Изменение профиля может изменить учитываемую историю; смешение профилей универсального ученика не является проверкой профессиональной специализации.

## Достаточность и достоверность

В выборку входят только `submitted`/`reviewed` с временем завершения и допустимым баллом 0–100. Без покритериальных решений достаточно либо `requires_review == false`, либо общей оценки преподавателя с непустой причиной — поведение RC1 сохраняется. В RC2 после любого покритериального решения требуется **актуальное общее подтверждение** преподавателя именно текущей ревизии. До него попытка исключена, даже если автоматический балл был определён. Если прежнее подтверждение помечено `teacher_review_stale`, оно также не используется. Остановленные попытки исключаются по событию `teacher_stopped`, даже если общий разбор сменил их статус на `reviewed`. Активные, назначенные и неоднозначные неподтверждённые попытки не учитываются.

Политика `author-v2` рассматривает последние **10** подходящих попыток по времени завершения. Пороги и граница доверия RC2 сохранены; v2 меняет выбор сценария и его объяснение. При числе меньше **3** возвращаются `status: insufficient_data`, `proposed_level: null`, объяснение и фактический размер выборки. Предложения сценариев и слабые навыки при этом не формируются. `eligible_count` показывает полный размер подходящей истории; `sample_size` — размер используемого окна. Это число попыток, а не число разных сценариев или независимых наблюдений: повторы одного упражнения также входят в окно. Давность в календарных днях и эффект запоминания пока не моделируются.

## Прозрачные пороги

Средний балл берётся из актуального общего подтверждения преподавателя, если оно есть; иначе — из пригодной автоматической оценки отчёта без покритериальных решений. Отдельный балл `expert_assessment` помогает преподавателю проверить итог, но сам не становится итоговым доказательством для рекомендаций. Уровни не означают статус допуска:

| Условие на выборке не менее 3 попыток | Предложение |
| --- | --- |
| Средний балл ниже 60 **или** есть пригодный подтверждённый критический провал по правилам или решению преподавателя | `basic`: повтор базовых упражнений |
| Средний балл не ниже 85, нет подтверждённых критических провалов и повторяющихся слабых критериев | `advanced`: обсудить усложнение |
| Остальные случаи | `intermediate` |

Слабый критерий появляется только при минимум **3** определённых наблюдениях одного `(criterion_id, title)`, минимум **2** провалах и доле провалов не меньше **50%**. Возвращаются `failed`, `total`, `failure_rate`, а также ID попыток с провалом. Один промах остаётся в разборе попытки, но не объявляется устойчивой слабостью. Нулевые по баллам грамматика/подсказки не превращаются в слабый навык. Разные названия при одном авторском ID не объединяются; эквивалентность критериев между разными сценариями пока не доказана.

Общая экспертная оценка не является покритериальной разметкой. Если исходный отчёт требовал проверки или преподаватель изменил общий балл, неподтверждённые исходные критерии этого отчёта не используются для вывода слабостей и критических ошибок. В RC2 явное решение `pass`/`fail` по отдельному критерию становится пригодным свидетельством после актуального общего подтверждения, даже если общий балл вручную изменён. Оставленное преподавателем `review` не превращается в `fail` и блокирует использование прежнего автоматического статуса именно этого критерия. Остальные исходные критерии пригодны только при старом условии RC1: исходный `requires_review=false`, общий балл не менялся. Так исправление одного факта не подтверждает автоматически все другие.

Общий подтверждённый балл участвует в среднем; `criterion_evidence_attempts` показывает, по скольким попыткам есть пригодный хотя бы один критерий. Нулевые по весу критерии исключаются. Поэтому отсутствие слабостей может означать недостаток покритериальных данных: ответ говорит об этом прямо. При трёх высоких общих оценках усложнение может быть предложено без полного покритериального подтверждения; преподаватель обязан учитывать это ограничение. `GET /analytics` использует те же фильтры доверия для среднего и статистики критериев и отдельно возвращает `scored_sessions`.

## Ответ API

```json
{
  "policy_version": "author-v2",
  "min_sample_size": 3,
  "window_size": 10,
  "teacher_decides": true,
  "items": [{
    "student_id": "student-id",
    "student_name": "Учебный участник",
    "status": "recommendation",
    "sample_size": 3,
    "eligible_count": 3,
    "proposed_level": "intermediate",
    "average_score": 83.33,
    "reason": "Авторская политика author-v2, последние 3 проверенных попытки…",
    "evidence_session_ids": ["attempt-3", "attempt-2", "attempt-1"],
    "criterion_evidence_attempts": 3,
    "weak_skills": [{
      "criterion_id": "workflow",
      "title": "Действия с карточкой",
      "failed": 2,
      "total": 3,
      "failure_rate": 0.667,
      "evidence_session_ids": ["attempt-2", "attempt-1"]
    }],
    "classroom": {
      "student_service": "Мосводоканал",
      "compatibility_rule": "Та же служба; универсальный сценарий; либо профиль ученика «Учебная ДДС».",
      "compatible_scenario_count": 3
    },
    "suggested_scenarios": [{
      "id": "scenario-id",
      "title": "Вода из учебного колодца",
      "service": "Мосводоканал",
      "difficulty": "intermediate",
      "selection_basis": "rubric_match",
      "matched_criteria": [{"criterion_id": "workflow", "title": "Действия с карточкой"}]
    }],
    "scenario_selection_reason": "В сценариях совпадают критерии из проверенной истории; условия упражнения проверяет преподаватель.",
    "unmatched_criteria": [],
    "teacher_decides": true
  }]
}
```

Предлагается до пяти утверждённых сценариев совместимой службы и предложенной сложности. Преподаватель видит свою библиотеку и seed; ученик — краткие названия seed и ранее назначенных ему сценариев. Скрытые ожидаемые действия, ответы контактов и эталоны не возвращаются.

При отсутствии повторяющихся слабых критериев `selection_basis=profile_level`: это только подбор по профилю и уровню. При наличии слабостей допускается `rubric_match`: сценарий должен содержать хотя бы один совпадающий критерий. Для встроенных критериев открытия, времени, статусов и звонка проверяются известные ID/названия и наличие соответствующего условия в новом сценарии и снимках провальных попыток. Для смыслового факта нужны точные ID и подпись, непустые варианты и проверяемое происхождение в каждом снимке с провалом. Если хотя бы в одном таком снимке требовалось предварительное подтверждение контактом, оно обязательно и в кандидате. Неполные/неоднозначные связи не дают совпадения.

Совпавшие ID/названия из уже известной слабости возвращаются в `matched_criteria`. Будущие формулировки, контакты и их ответы не раскрываются. Сначала показываются сценарии с большим числом совпадений, затем стабильный порядок названия/ID; максимум пять. `unmatched_criteria` перечисляет слабые критерии, не покрытые реально показанными предложениями. `scenario_selection_reason` объясняет совпадение, обычный подбор либо пустой результат. Если среди данной службы/уровня совпадений нет, список пуст; сложность не меняется автоматически.

Это совпадение рубрики, а не доказанное воздействие упражнения на навык. Одинаковые ID/подписи могут скрывать разные авторские условия; преподаватель проверяет содержание перед назначением. Переименованный эквивалентный критерий может быть пропущен. Валидированная таксономия навыков, перенос и оптимальная частота повторения пока отсутствуют.

## Сценарии полного цикла

К исходным шести seed добавлены два синтетических упражнения:

- **Полный цикл: восстановление водоснабжения** — `accepted → responding → arrived → completed`, учебный 2001 подтверждает направление, 2002 сообщает прибытие и завершение. Время работ сжато, второе сообщение шаблонное. Проверяемые факты: адрес, направление, прибытие, восстановление воды.
- **Мотивированный отказ после уточнения принадлежности** — `accepted → refused`. Контакт подтверждает обслуживание другой организацией и принятую передачу. В условии упражнения это основание отказа данной ДДС. Оно не объявляется реальным правилом маршрутизации.

`rejected` («Не принято») до принятия проверяется отдельным производным сценарием подтверждённого дубля в тесте. Это другая ветка, а не следующий шаг после `refused`. Преподаватель может создать такой сценарий существующим редактором.

Оценщик проверяет последовательность статусов и ограниченные текстовые факты. Для двух новых упражнений добавлено условие происхождения факта: направление подтверждает контакт `dispatch-officer` (2001); прибытие и восстановление воды — `brigade-leader` (2002); основание отказа и передачу — `ownership-officer`. Без нужного второго звонка корректные слова о прибытии и завершении не дают соответствующих баллов.

Критерий может содержать `confirmed_by_contact_ids: ["brigade-leader"]`. Поле необязательно; пустой список сохраняет прежнюю текстовую проверку. Несколько ID означают любой один разрешённый контакт. При утверждении сценария сервер проверяет существование этих ID в `contacts`. Поле входит в неизменяемый снимок назначения и до сдачи скрыто от ученика вместе с рубрикой.

Подтверждением считается только цепочка серверных событий: соединённый `call_started` с разрешённым `contact_id` → непустой `trainee_message` того же `call_id` → последующий `contact_message` на ещё открытом звонке, содержащий подтверждение факта → собственное корректное утверждение ученика. Приветствие до первого доклада, другой контакт и чужой `call_id` не подходят. Ответ контакта сам по себе не оценивается как текст ученика. Содержание ответа проверяется теми же ограниченными правилами: отрицание не подтверждает факт; неопознанный перефраз или противоречивый ответ передаются преподавателю. Последний ответ до утверждения ученика учитывается вместо устаревшего положительного.

Проверяется **первое** положительное утверждение ученика: последующий звонок не оправдывает преждевременную запись задним числом. Повтор факта после такого звонка не стирает замечание. В evidence успешного критерия входят ID начала звонка, запроса, подтверждающего ответа и утверждения ученика. Порядок основан на сохранённой серверной последовательности, а не на времени, сообщённом браузером.

Это причинный порядок конкретного авторского упражнения, не универсальная модель реального реагирования. Шаблонный ответ 2002 сообщает прибытие и завершение вместе, временная длительность работ не моделируется; правильный порядок всех статусов проверяется отдельно. Отрицания, сложные перефразы и противоречия вне проверенного словаря требуют отдельного разбора. Новые seed и условия не заменяют уже сохранённые сценарии в БД или снимки назначений: seed загружается только при отсутствии его ID. Для старой демобазы требуется явно создать/утвердить обновлённую копию сценария либо использовать новую изолированную БД.

## Проверка и следующий продуктовый шаг

```sh
cd backend
.venv/bin/python -m pytest tests/test_recommendations.py tests/test_full_lifecycle.py tests/test_confirmation.py -q
```

Тесты проверяют корректные полные ветки на 100, отсутствие основания отказа, неправильный порядок, валидность восьми seed, пороги/окно/невалидные баллы, недостаток данных, экспертный пересмотр, профиль службы, изоляцию ролей/учеников/преподавателей, остановку после review и отсутствие побочных назначений. Дополнительно проверяются отсутствие второго звонка, преждевременное прибытие, приветствие вместо ответа, другой контакт/call_id, отрицательный и неоднозначный ответы, устаревшее подтверждение, сохранение/валидация новых полей и скрытие рубрики от ученика. Это программная проверка политики, не проверка педагогической эффективности.

До заявления об эффективности нужны согласование критериев и порогов методистом, покритериальное экспертное подтверждение, разные сценарии переноса навыка и пилот со сравнением повторной ошибки после предложенного упражнения. Пользовательского исследования или такого пилота пока не проводилось.

Покритериальный интерфейс RC2 прошёл техническую интеграционную и браузерную проверку; его контракт и защита от конфликта ревизий описаны в [api-contract.md](api-contract.md), а статус поставки — в [release-readiness.md](release-readiness.md). Подготовлен [протокол пилота](pilot-protocol.md) с пустыми [формами наблюдения](pilot-templates/README.md). Экономия времени преподавателя, снижение ошибок и полезность автоматических рекомендаций на людях пока не измерялись.
