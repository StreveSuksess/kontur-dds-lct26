# Резервная копия и восстановление

Проверенный путь MVP — SQLite, Python 3.11+ и стандартная библиотека. Скрипты работают с локальными файлами и не переключают работающий сервер на восстановленную БД. Команды ниже выполняются из корня проекта; путь `--source` должен соответствовать фактическому `DATABASE_URL`.

## SQLite: создать копию

```sh
mkdir -p backups
python3 scripts/backup.py \
  --source backend/var/dds.db \
  --destination backups/dds-20260919-01.sqlite3
```

Используется SQLite online backup API: в копию попадает согласованное состояние, включая зафиксированные записи из WAL. Обычное копирование одного `.db` при работающем сервере не заменяет эту процедуру. Источник открывается в режиме read-only; скрипт не изменяет его записи и схему. Работающее приложение может продолжать собственные записи.

Успех — код выхода `0` и JSON с SHA-256, размером, числами строк семи таблиц и абсолютными путями. Сообщение не содержит содержимого карточек, паролей или cookie. Ошибка — ненулевой код и объяснение в stderr. `--timeout 120` меняет бюджет копирования/SQL-проверок; по умолчанию 60 секунд, допустимо до 3600. Это не гарантия остановки зависшего файлового хранилища за заданное время.

## SQLite: восстановить в новый файл

```sh
python3 scripts/restore.py \
  --source backups/dds-20260919-01.sqlite3 \
  --destination backups/dds-restored-check-01.sqlite3
```

Восстановление разрешено **только в несуществующий файл**. Опции `--force` нет. Существующий файл, символическая ссылка назначения и старые `-wal`, `-shm`, `-journal` рядом с назначением приводят к отказу. Каталог назначения должен существовать. Исходная рабочая БД и файл резервной копии остаются на месте.

Перед публикацией результата скрипт проверяет:

- точный набор семи таблиц: `users`, `auth_sessions`, `scenarios`, `training_sessions`, `events`, `audit`, `intake112_attempts`; резервная копия прежней схемы v1 требует отдельной миграции;
- ожидаемые столбцы, первичные и внешние ключи, глобальную уникальность имени пользователя и идентификатора события внутри попытки;
- отсутствие триггеров и представлений;
- `PRAGMA integrity_check` и `PRAGMA foreign_key_check`;
- повторную целостность после удаления всех записей `auth_sessions` и нулевое число оставшихся токенов.

Схема проверяется **до** удаления токенов: повреждённая ссылка из токена на отсутствующего пользователя не маскируется очисткой. Неизвестные изменения схемы требуют согласованного обновления проверяющего кода, автоматической миграции здесь нет. Проверка структуры не является доказательством подлинности содержимого копии или полной эквивалентности каждого свойства схемы.

Сохраняются пользователи и хеши паролей, сценарии, снимки назначений, события, черновики, отчёты, преподавательские коррекции и аудит. Старые cookie становятся недействительны **в восстановленной БД**; пользователи входят заново с прежними паролями. Сессии исходного работающего приложения не отзываются. Восстановление демобазы сохраняет демонстрационные аккаунты и само по себе не превращает её в production-конфигурацию.

Результат создаётся во временном файле в том же каталоге, проверяется, переводится в самостоятельный SQLite-файл без необходимого WAL и синхронизируется на диск. Права файла — `0600`. Для атомарной публикации без риска перезаписи используется `link(temp, destination)` с последующим удалением временного имени: обычный POSIX `rename` мог бы перезаписать файл, появившийся между проверкой и публикацией. Поэтому файловая система должна поддерживать hard links. При обычной ошибке временные файлы удаляются; аварийное завершение процесса может оставить скрытый временный файл, но не публикует неполную БД. Ошибка синхронизации каталога после публикации может вернуть ненулевой код при уже существующем полном файле: сначала проверьте результат, не пытайтесь его перезаписывать.

Перед использованием восстановленного файла оператор отдельно запускает изолированную проверку соответствующей версии приложения, проверяет числа строк и известную карточку/оценку, недействительность старого cookie и новый вход. Переключение рабочего `DATABASE_URL` — отдельная операция с остановкой соответствующего сервера; скрипты её не выполняют. Для текущего приложения рекомендован один worker. Модели AI, исходные документы, конфигурация, файлы классификатора и знания вне БД в эту копию не входят — их версии сохраняются отдельно вместе с поставкой.

SHA-256 позволяет сравнивать файлы, но не подписывает их и не шифрует данные. Ротация, удалённое хранение, шифрование и расписание не реализованы. JSON-экспорт администратора не является входом для этих SQLite-скриптов.

## Проверенные тесты

```sh
python3 -m unittest discover -s tests -p test_backup_restore.py -v
```

Набор проверяет полный roundtrip, известные русскоязычные тексты и количества строк, неизменность исходного закрытого файла, удаление токенов, отказ перезаписи в том числе при гонке, повреждённую схему/FK, недоверенный триггер, некорректный файл, dangling symlink, WAL и CLI-коды завершения. Дополнительный тест в `backend/.venv` создаёт настоящее приложение, проходит назначение → обработку → отправку → преподавательскую коррекцию → backup → restore и проверяет точное сохранение событий/отчёта, ответ `401` старому cookie и успешный новый вход. Если backend-окружения нет, этот тест явно отмечается `skipped`, а не считается выполненным.

## PostgreSQL: отдельная непроверенная здесь процедура

**PostgreSQL backup/restore в этой среде не выполнялся.** SQLite-скрипты не принимают PostgreSQL URL. Для отдельной проверки PostgreSQL используйте штатные утилиты и заранее подготовленные локальные connection services без паролей в командной строке. Пример ниже предполагает `dds_source` для источника, `dds_maintenance` для административного подключения к целевому кластеру и `dds_restore_check` строго для новой тестовой БД `dds_restore_check_20260919`. Не направляйте последний service на рабочую БД.

`pg_dump` создаёт согласованный логический экспорт одной базы; глобальные роли и tablespaces требуют отдельного учёта. Версия клиента не должна быть старше major-версии исходного сервера. Это пример переноса и проверки MVP, не проверенная production-стратегия аварийного восстановления. [Документация pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), доступ 19.09.2026.

```sh
umask 077
dds_backup_dir="$(mktemp -d ./backups/pg-dds.XXXXXX)"
pg_dump --dbname="service=dds_source" --format=custom \
  --file="$dds_backup_dir/dds.dump"
```

Каждую команду выполнять только после успешного завершения предыдущей. Создайте **новую** пустую БД; не используйте `--clean` или удаление существующей БД. `createdb` поддерживает maintenance connection string. [Документация createdb](https://www.postgresql.org/docs/current/app-createdb.html), доступ 19.09.2026.

```sh
createdb --maintenance-db="service=dds_maintenance" \
  --template=template0 dds_restore_check_20260919
pg_restore --dbname="service=dds_restore_check" \
  --single-transaction --exit-on-error --no-owner \
  "$dds_backup_dir/dds.dump"
psql --dbname="service=dds_restore_check" -X --set=ON_ERROR_STOP=1 \
  --command="DELETE FROM auth_sessions; SELECT count(*) AS remaining_tokens FROM auth_sessions;"
```

`--single-transaction` делает восстановление дампа одной транзакцией; очистка сессий выше — отдельная команда, поэтому целевое приложение до её успеха не запускается. Используйте собственный доверенный дамп: восстановление PostgreSQL выполняет SQL из источника. Владение, права доступа и наличие требуемых ролей нужно проверить для конкретного кластера. [Документация pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html), доступ 19.09.2026.

Перед допуском PostgreSQL-варианта нужны собственный интеграционный прогон: сверка всех семи таблиц, ключей и ограничений с версией приложения; количество строк и известные тексты; ноль `auth_sessions`; старый cookie → `401`; новый вход; сохранность отчёта, коррекции и аудита. Успех SQLite-тестов не заменяет этот прогон.
