# Проверка сценария и обоснованный подбор следующей практики

Дата: 2026-09-26. Основание: повторный продуктовый аудит, пять первичных исследований в `memory-bank/research/2026-09-26-learning-feedback-research.md` и воспроизведение алгоритма на синтетической истории. Telegram Q&A этой недели не прочитан: инструмент доступа к открытому приложению недоступен.

## Наблюдаемые проблемы

1. В предпросмотре перед утверждением нет двух лимитов, реплик контактов и конкретной связи смыслового критерия с подтверждающим контактом. Проверка этих данных требует отдельного перехода в редактор.
2. На трёх синтетических провалах `fact:arrival` из полного водного сценария текущий подбор предлагает «Отключение воды в учебном доме». В его рубрике только `address` и `dispatch`: прибытие не проверяется. Подбор учитывает службу и сложность, а UI называет упражнения подходящими рядом со слабым критерием.

Это воспроизводимые свойства продукта. Экономия времени преподавателя и улучшение обучения пока не измерены.

## Изменение

### Полная проверка перед утверждением

Предпросмотр показывает два лимита отдельно, сложность/версию, полную исходную карточку (включая «нет сведений» о пострадавших), контакты с именем, ролью, учебным номером, приветствием и ответом после доклада. Для каждого смыслового критерия видны варианты формулировок, критичность и имена/номера разрешённых подтверждающих контактов. Если данные отсутствуют, это явно указано. Преподаватель сопоставляет ответ контакта с ожидаемым фактом; интерфейс не выдаёт такое сопоставление за автоматическую проверку содержания.

Это только преподавательский просмотр. Ответы, эталон и будущие критерии не добавляются в API ученика. Утверждение остаётся явным существующим действием.

### Подбор по имеющемуся критерию

- Авторские пороги 3/10/60/85 и правила доверия к отчётам сохраняются.
- Версия политики подбора — `author-v2`. Сначала сохраняются фильтры утверждённости, области доступа, службы и уровня.
- При отсутствии повторяющихся слабых критериев список прямо называется подборкой по профилю и уровню.
- При наличии слабостей сценарий попадает в список, только если содержит хотя бы один совпадающий критерий. Для фактов требуется точная пара `fact:id` + `label`; один ID, название сценария или похожее слово не подтверждают совпадение.
- Для факта, проваленного в сценарии с предварительным подтверждением от контакта, новый сценарий тоже должен требовать такое подтверждение. Если происхождение факта в сохранённом снимке невозможно проверить, сопоставление по нему не делается. Несколько исходных вариантов проверяются консервативно: хотя бы один с обязательным подтверждением требует его и в кандидате.
- Встроенные критерии времени, последовательности статусов и исходящего доклада сопоставляются по фиксированным ID/названию и наличию соответствующих условий в сценарии. Не делать вывод о педагогической эквивалентности этих условий.
- Сначала показываются сценарии, покрывающие больше найденных критериев; затем стабильный порядок по названию/ID, максимум пять.
- Ответ включает для каждого предложения только совпавшие названия/ID из уже известной слабости; будущие эталонные фразы, контакты и лимиты не раскрываются.
- Если совпадений нет, возвращается пустой список и ясная причина. Непокрытые критерии перечисляются отдельно; обычный сценарий той же сложности не выдаётся за отработку отсутствующего критерия.
- Учебное назначение остаётся решением преподавателя. Совпадение рубрики — объяснимый фильтр, а не доказательство переноса навыка или валидированная адаптация.

## Проверки

### Дополнение по новому материалу заказчика

В памятке «Работа с АРМ-112 для ДДС от ОКр_ГСИ.pdf», с.21, открытие и «Принята/Не принята» разделены; 30 секунд относятся к первому решению после направления карточки. Сама памятка названа неофициальной. Q&A связывает 30 секунд с открытием; эти источники не объединяются в один норматив.

В отчёте добавить нейтральное наблюдение «Первое решение по карточке»: первое сохранённое `status_changed` со статусом `accepted` или `rejected`, его время от начала попытки и точный статус. Открытие, текст «карточка принята» и другие статусы не заменяют решение. Если его нет — «Не зафиксировано». При разрыве связи предупредить о времени серверной записи. Наблюдение строится из журнала, доступно и для существующих попыток, не меняет отчёт/баллы/лимиты задним числом и не заявляет соблюдение реального регламента.

Backend: воспроизведённый `arrival` не рекомендует `dispatch`-only; точный факт совпадает; один ID при другой подписи не совпадает; обязательное подтверждение не ослабляется; отсутствие проверяемого снимка не создаёт совпадение; частичное покрытие и порядок детерминированы; текущие ограничения ролей/остановленных/stale-отчётов сохраняются; новый ответ не раскрывает скрытые данные.

UI: все данные предпросмотра видны, длинные реплики переносятся; «нет сведений» не становится «нет пострадавших»; совпавшие и непокрытые критерии различимы; подбор по уровню явно отличается от совпадения рубрики. Сборка TypeScript/Vite и серверные регрессии обязательны. Если GUI-инструмент недоступен, использовать локальную проверку рендера и явно не заявлять реальную браузерную проверку.

Пилот: сопоставимое задание преподавателю на поиск двух заранее внесённых противоречий и выбор следующего упражнения. Измерять обнаруженные ошибки, ложные совпадения, число переходов и полное время. Нужен новый эквивалентный случай для оценки переноса; повтор знакомого сценария сам по себе его не доказывает.

## Защита от неподдержанной версии классификатора

Аудит 046.24 выявил сдвиг «Главной службы» с N в M и дополнительные маршрутные столбцы после CL. Текущий позиционный импортёр не должен молча читать такой файл как046.11. Добавить проверку поддержанной схемы заголовков M/N и отсутствия непустых маршрутных данных вне поддержанного диапазона; при несовпадении — понятный отказ до записи output. Проверенная046.11 импортируется как раньше; производные данные приложения остаются прежними. Миграция на046.24 и предметная проверка новых маршрутов в эту правку не входят.
