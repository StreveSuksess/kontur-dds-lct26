# RC2: покритериальное решение преподавателя

## Проблема и основание
В RC1 общий балл преподавателя не говорит, какой спорный критерий он разрешил. При общей коррекции recommendations исключает все исходные критерии попытки. В живом UI малая LLM дала ложные замечания, а правила сознательно возвращают review. Центральная задача преподавателя — проверить конкретное действие с доказательством, поэтому адресная коррекция приоритетнее настройки весов. Это гипотеза ценности по Q&A/поведению прототипа; экономия времени ещё не измерена. Источники: docs/product-research.md, docs/ui-validation.md, docs/adaptation.md.

## Пользовательский поток
Преподаватель раскрывает критерий завершённой своей попытки, читает ожидаемое/фактическое и события, выбирает «Выполнено», «Не выполнено» либо «Оставить на проверке», вводит обязательное основание и сохраняет. Ученик видит решение и основание в своём разборе. Исходный вывод правил виден отдельно, никогда не переписывается. После решений преподаватель явно подтверждает общий итог существующей формой; ручной общий балл остаётся возможен с обоснованием.

## Контракт
Новый POST `/api/sessions/{id}/criterion-reviews`, teacher owner, только submitted/reviewed/stopped.

```json
{"criterion_id":"fact:address","status":"pass","comment":"Адрес передан в общеупотребительном сокращении без потери номера дома.","evidence_ids":["event-uuid"]}
```

status=pass/fail/review, comment послеstrip минимум3/максимум1999символов; evidence_ids необязателен, по умолчанию копирует criterion.evidence_ids. Максимум50 уникальныхID, каждый принадлежит данной попытке; чужой/несуществующийID422. criterion_id должен существовать в исходном report.criteria; неизвестный422. student/admin/чужойteacher403; незавершённая попытка409. Возврат полного Session с дополненным Report.

Добавочные поля Report, все обратно совместимы:

```json
{
 "criterion_review_revision":1,
 "criterion_reviews":{"fact:address":{"status":"pass","comment":"...","evidence_ids":["..."],"reviewed_at":"ISO UTC","reviewer_name":"...","revision":1}},
 "expert_assessment":{"score":100,"max_score":100,"requires_review":false,"critical_errors":0},
 "teacher_review_stale":false
}
```

`score`, `criteria`, `requires_review`, `generated_at` исходного отчёта НЕ меняются. expert_assessment рассчитывается из исходных весов и эффективных статусов: pass даётmax_points, fail/review0; любойreview сохраняетrequires_review (включаяgrammar0). Каждый пересмотр — append-only event`criterion_review_saved` сprevious/current и audit. Последние решения хранятся вmap; история не теряется.

Если общийteacher_review уже существовал, новое решение помечаетегоstale=true; reviewed-попытка возвращаетсяsubmitted, старый общий результат остаётсявидимым как предыдущий. POST/review явно подтверждает итог, сбрасываетstale, сохраняетcriterion_revision и аудитпредыдущейоценки. Stopped-попытки всегда исключены изадаптации через teacher_stopped event.
