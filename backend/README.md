# Контур ДДС — локальный сервер

Сервер учебного тренажёра, а не действующая Система-112. Синтетическая карточка поступает ученику, который открывает её, выполняет действия ДДС, набирает учебный номер и пишет доклад должностному лицу. Преподаватель назначает задания и проверяет разбор.

## Запуск

Из каталога `backend`:

```sh
uv sync --python 3.12
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

При доверенном корпоративном центре сертификации uv может потребоваться `--system-certs`; TLS-проверку отключать не требуется. Python и зависимости устанавливаются в локальное окружение `.venv`. Конкретные версии зафиксированы в `uv.lock`.

Документация API: `/docs`. Проверка состояния: `/api/health`. Если `frontend/dist` собран, FastAPI отдаёт его с того же origin. В разработке frontend использует proxy `/api`.

По умолчанию включён синтетический демонстрационный режим. Логины `teacher`, `student`, `admin`, `student_water`, `student_bridge`, `student_lift`, пароль `Demo112!`. Последние три ученика имеют профили Мосводоканал, Гормост и Мослифт. `student` имеет универсальный учебный профиль. Seed-сценарии являются демонстрационными утверждёнными шаблонами; это не утверждение методистом заказчика. Их можно назначать или копировать в собственный черновик, но нельзя менять исходный шаблон.

Для нового недемонстрационного контура задать `DEMO_MODE=false`, уникальный `BOOTSTRAP_ADMIN_PASSWORD` длиной от 12 символов и отдельную новую `DATABASE_URL`. Переключение `DEMO_MODE` на уже созданной демонстрационной БД **не удаляет прежние демонстрационные учётные записи и их пароли**. Использовать новую БД; не переносить демонстрационную БД в рабочий контур. Bootstrap создаёт администратора только если в БД ещё нет администратора.

Параметры в `.env.example`. Для PostgreSQL — `postgresql+psycopg://...`. SQLite использует WAL, foreign keys и busy timeout. Сервер имеет процессный mutex для учебных mutations; проверенный исходный режим — один worker. Для HTTPS включить `COOKIE_SECURE=true`; доверенные browser origins перечислить в `ALLOWED_ORIGINS`. Защита от cross-site mutation включена; токен входа хранится хешированным в БД, cookie имеет HttpOnly и SameSite=Strict.

## Тесты

```sh
uv run pytest -q
```

Каждый интеграционный тест использует `create_app(Settings(database_url=...))` и временную SQLite БД. Проверяются роли и владельцы, закрытый эталон, approve gate, снимки версий, идемпотентность при конкурентной повторной отправке, весь учебный цикл, два пересмотра оценки, CSV, блокировка аккаунта и восстановимое содержимое backup. Семантические тесты отдельно проверяют отрицания, вопросы, будущее и правильные формулировки.

Набор `/docs/validation-cases.json` в корне репозитория — независимый диагностический seed. У него иной, более широкий предметный охват, включая создание карточки112, отсутствующее в текущем MVP. Нельзя объявлять все его случаи поддержанными только на основании unit-тестов.

## Основные модули

- `app/main.py`: фабрика приложения, startup, данные справочников и HTTP security boundary.
- `app/config.py`, `app/db.py`, `app/models.py`: настройки, соединения, таблицы.
- `app/auth.py`: хеширование паролей, сессии входа, зависимости RBAC.
- `app/common.py`: scope владельца, сериализация без скрытого эталона для ученика, журнал.
- `app/routes/scenarios.py`: черновик, копирование, утверждение, версия, архив, генератор шаблона.
- `app/routes/sessions.py`: назначения, попытки, черновики, события, программный телефон, разбор, review и CSV.
- `app/assessment.py`: объяснимый ограниченный разбор по правилам.
- `app/simulation.py`: базовый локальный шаблонный собеседник; никакие реальные номера не вызываются.
- `app/routes/reference.py`: справочники, пользователи и scoped analytics.
- `app/routes/admin.py`: учётные записи, аудит и локальные резервные копии.
- `data/scenarios.json`: шесть синтетических сценариев с provenance типа происшествия.

Полный контракт находится в `../docs/api-contract.md`. Расширения локального AI/голоса могут добавляться отдельными модулями; фактический режим нужно читать из API и результатов проверки, а не из наличия конфигурационного URL.

## Ограничения правил оценки

Начальная реализация использует формальные события и ограниченный анализ текста. Она не обучалась на данных заказчика и не является официальной аттестацией. Ненайденное текстовое соответствие у непустого ответа обычно получает `review`, чтобы не штрафовать неизвестный перефраз. Очевидное отрицание или будущее не считается выполненным направлением. Грамматика проверяется небольшим локальным словарём и не отнимает баллы за правильный факт.

`score` — автоматически подтверждённые баллы. Когда `requires_review=true`, это предварительная оценка: непроверенные критерии ещё не получили подтверждённых баллов. `teacher_review` хранится отдельно. Исходные `score`, `criteria` и время генерации не переписываются при экспертной оценке; все пересмотры сохраняются в событиях. Аналитика использует экспертный балл при его наличии, иначе автоматический; это не доказательство роста квалификации.

30 секунд до открытия и 180 секунд до сдачи — изменяемые **учебные** параметры. Время сервера не считается точной активной длительностью ученика при потере сети: `connection_restored` переводит временные критерии на ручную проверку. Точная семантика неизвестных формулировок, полнота текста и образовательный эффект требуют отдельного пилота.

## Резервные копии

`POST /api/admin/backup` доступен только администратору. База не отправляется браузеру. Возвращаются имя, дата и размер локального файла в `BACKUP_DIR`; права файла 0600.

Для SQLite используется штатный online backup API: файл `.sqlite3` содержит согласованную БД, включая локальные учётные записи и действующие хеши сессий входа. Хранить его как закрытые данные. Для PostgreSQL формируется `.json` в repeatable-read транзакции, формат `dds-logical-backup-v1`; `auth_sessions` из логической копии исключены. Это не `pg_dump` и не доказательство готового production-процесса аварийного восстановления.

Восстановление SQLite проверять в отдельном контуре: остановить целевой сервер, скопировать backup в **новый** путь БД, выполнить `PRAGMA integrity_check`, сравнить число попыток/событий, удалить записи `auth_sessions` перед предоставлением доступа, указать новую `DATABASE_URL` и проверить чтение ранее завершённой попытки. Не подменять файл работающей БД и не удалять текущие данные в ходе проверки восстановления. Полную эксплуатационную процедуру восстановления/ротации следует согласовать для развёртываемого контура.
